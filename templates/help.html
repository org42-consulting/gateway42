Overview

Gateway42 is a secure, multi-user API gateway for local and remote AI inference backends. It sits between your users and your inference engines, exposing an OpenAI-compatible API while adding authentication, logging, and rate limiting. Supported backends: oMLX (local, Apple silicon), managed from this page, and any OpenAI-compatible endpoint — vLLM, LM Studio, llama.cpp, or the real OpenAI API.

  • OpenAI-compatible API — clients built for the OpenAI API work with Gateway42 without modification — just swap the base URL and API key.
  • Multiple engine backends — connect oMLX instances and OpenAI-compatible endpoints; manage them from the Settings page without restarting.
  • API key authentication — every user receives a unique key; only active users can send requests.
  • Per-user rate limiting — configurable maximum requests per minute per user.
  • Daily token quotas — optional per-user budget of tokens per day (input + output combined), enforced alongside rate limiting.
  • HTTP request logging — every API request is recorded with timestamp, client, IP, method, path, and status code.
  • AI interaction logging — prompt and response for each chat completion, stored per user and exportable as CSV.
  • Admin dashboard — manage users, configure engines, search for and download models, and review logs.

Dashboard

The Dashboard is the main landing page after login. Its panels cover:

Engine Status

Displays whether the configured inference engines are reachable, along with their connection details and the list of available models. This panel is refreshed every time the page loads. If an engine is unreachable, its status shows INACTIVE and its model list is unavailable. Configure engines on the Settings page.

Token Usage

Token totals for chat requests over the last 24 hours, 7 days, or 30 days, grouped by client and then by the model that served the request. Clients are ranked by total tokens; the bar shows each client's share against the largest one in the window. Counts come from the request log the gateway already writes, so nothing is sampled, and the figures are abbreviated to three significant figures — exact numbers are on the Logs page.

A request whose engine returned no usage is counted as unreported and labelled as such, rather than added to the total as a zero: unmeasured is not the same as free. in_tokens is what the engine counted as input and out_tokens what it generated. Deleted clients keep their history and are marked DELETED.

Token Quotas

The daily token budget per client, reset at UTC midnight, with used and remaining figures and a bar showing how much of the budget is consumed. Only clients with a positive budget are listed; unlimited clients have no row, so a fleet with no budgets renders no panel. Set or clear a budget from the Token quota column of the client table below.

Registered Users

Register New User

Enter a client name and click Register User. A unique API key is generated automatically and displayed on the next page. The user starts in DISABLED status — activate them manually once you have shared their API key securely.

Reset System

Permanently deletes all HTTP request logs and all AI interaction logs, then discards every in-memory rate-limit bucket, so any user currently being throttled is immediately free to burst again. User accounts and engine configurations are not affected. A confirmation dialog is shown first. The log deletion cannot be undone.

Settings

The Settings page is where you configure your inference backends. Two engine types are supported. Changes take effect immediately — no restart required.

Engine Types

TypeDescription
oMLX A local (or LAN-accessible) oMLX server, e.g. http://127.0.0.1:8000. Give it oMLX's main API key: besides inference, the gateway uses it to manage the engine's models (download, load, unload, delete) and to run the tools of oMLX's MCP servers.
OpenAI-compatible Any other endpoint that speaks the OpenAI API — vLLM, LM Studio, llama.cpp, or the real OpenAI API. Provide the base URL and an API key if required. The base URL works with or without its /v1. Requests pass through without translation.

Engine Management

For each engine you can:

  • Add — name it, select the type, and provide the base URL (with its port) and the API key.
  • Edit — update an existing engine's connection details or API key. Leave the API key blank to keep the current one; it is never shown back.
  • Remove — delete an engine you no longer need.
  • Test Saved Engines — probe every engine already added. Typed-in values are not tested; click Add Engine first. A refusal shows the engine's status and reason, e.g. 401 Unauthorized: Invalid API key.

Engine Selection

When a request arrives at /v1/chat/completions, Gateway42 routes it to an engine that actually holds the requested model. The routing table is built from the same health probes shown on this page, so adding a model to an engine makes it routable without any configuration. When two engines report the same model, the one added first wins.

A model that no reachable engine reports gets 404 rather than being forwarded somewhere it will fail. A request with no model falls back to the first configured oMLX engine, or the first engine of any type if there is none.

Model Management (oMLX engines)

Lists every configured engine with its reachability status and, for reachable ones, the models on it. An engine that cannot be reached shows an INACTIVE badge and an empty model list. For oMLX engines each model shows whether it is loaded (● loaded, ◐ loading, ○ not loaded), read live from oMLX.

  • Load / Unload (oMLX engines) — loads the model into memory, or frees the memory it holds. Loading a large model can take a while; the page waits for it.
  • Delete (the × on a model tag, oMLX engines) — removes that model's weights from that engine's disk. A confirmation dialog is shown first. Logs that referenced the model are not affected.
  • Remove — deletes the engine from Gateway42's configuration. It does not touch the engine itself or any models on it.

Download Models (oMLX engines)

Search MLX models on Hugging Face through oMLX. Enter a name or keyword (e.g. Qwen3 8B) and click Search; results show the repository, its size and its download count.

Each result has a Download button that has oMLX download the model — with several oMLX engines, choose which one in the selector next to Search. A live progress bar shows the bytes transferred. The download runs on the oMLX engine: closing the page stops only the progress display. The model is routable as soon as the download finishes. Model management needs the engine's main oMLX API key.

Change Admin Password

Updates the admin account password. Requirements: at least 8 characters, one uppercase letter, one lowercase letter, and one digit. You must provide the current password to confirm the change.

Reset System

Same as the Reset System action on the Dashboard — see above for details.

Logs

Gateway42 maintains two layers of logs. The Logs page shows the HTTP request log — every request to /v1/ endpoints, most recent first, paginated 10 entries per page. The AI interaction log (prompt and response per completion) is stored per user and accessible via the Export CSV button on each user's row in the Dashboard.

Both tables are pruned automatically: rows older than GW42_LOG_RETENTION_DAYS (default 30) are deleted by a sweep that runs at startup and hourly thereafter. This matters most for the AI interaction log, which holds full prompts and responses — without pruning it grows with traffic and keeps user content indefinitely. Set the variable to 0 to keep everything.

The search field filters logs by username, path, or IP address. Results update on submission. Click Clear to reset the filter.

Export CSV

Downloads all HTTP request log entries (not just the current page) as a CSV file with columns: id, timestamp, method, path, client_ip, client_name, status_code.

API Usage

Gateway42 exposes an OpenAI-compatible API. Any client or library that targets the OpenAI API can be pointed at Gateway42 by changing the base URL and providing a Gateway42 API key.

Base URL

Replace the OpenAI base URL with your Gateway42 host:

http://<your-host>:7000/v1

Authentication

Pass the user's API key as a Bearer token in the Authorization header:

Authorization: Bearer <api_key>

Requests with a missing, invalid, or deactivated key are rejected with 401 Unauthorized.

Endpoints

EndpointMethodDescription
/v1/models GET Returns the combined catalogue of every reachable engine, in OpenAI format.
/v1/chat/completions POST Chat completion endpoint. Accepts OpenAI-format request bodies. Set "stream": true for Server-Sent Events streaming.
/health GET Returns {"status": "ok"}. No authentication required. Useful for uptime monitoring.

Example — cURL

curl http://<host>:7000/v1/chat/completions \
  -H "Authorization: Bearer <api_key>" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen3-8B-4bit",
    "messages": [{"role": "user", "content": "Hello!"}]
  }'

Example — Python (openai SDK)

from openai import OpenAI

client = OpenAI(
    base_url="http://<host>:7000/v1",
    api_key="<api_key>",
)

response = client.chat.completions.create(
    model="Qwen3-8B-4bit",
    messages=[{"role": "user", "content": "Hello!"}],
)
print(response.choices[0].message.content)

Parameters

Every engine speaks the OpenAI API, so the standard OpenAI parameters pass through without translation: temperature, top_p, seed, max_tokens, max_completion_tokens, frequency_penalty, presence_penalty, stop, response_format, tools, tool_choice, and others.

stream_options is the exception, and it is changed in your favour rather than dropped: on a stream, include_usage is forced on so the request can be measured, and your other sub-fields are forwarded unchanged. The practical effect is that a streamed response always ends with a usage chunk, even if you asked not to get one. It carries an empty choices array, so index defensively rather than assuming every chunk has a choice. On a non-streaming request the field is dropped, since it describes a stream that is not happening.

A stream is bounded by silence, not by how long it runs: it is closed after 60s in which the engine sent nothing, or after 30 minutes in total. A completion that keeps producing tokens is never cut for running long, so a long agent turn arrives complete. A non-streaming completion sends nothing until it is finished and so keeps a single 120s budget, with the 30s response-header limit tighter in practice — stream anything that may generate at length.

Rate Limiting

Gateway42 enforces a per-user token bucket. A user configured for N requests per minute gets a bucket holding N tokens that refills continuously at N ÷ 60 tokens per second. Each request spends one token; a request that arrives with the bucket empty is rejected with 429 Too Many Requests.

In practice that means an idle user can burst up to N requests back to back, and thereafter sustains N per minute. There is no fixed window boundary to wait for — capacity returns gradually, so a single token is available again roughly 60 ÷ N seconds after the bucket empties.

  • The default rate limit for new users is set by the DEFAULT_RATE_LIMIT environment variable (default: 10 req/min).
  • Each user's limit can be adjusted individually from the Dashboard. Changing it rebuilds that user's bucket, which also refills it.
  • Buckets live in memory, not in the database, so they are also cleared by a gateway restart. A user's bucket is discarded when they are deleted, and the Reset System action discards every bucket at once.
  • Because buckets are per-process, running more than one Gateway42 instance behind a load balancer multiplies the effective limit by the number of instances.
